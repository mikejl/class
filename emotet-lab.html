Briefing

Emotet began as a banking trojan in 2014 and has since evolved into a modular loader used to hand off follow-on payloads for other criminal groups, including operators behind Trickbot and Ryuk. It spreads mainly through phishing documents and malicious links, and it has repeatedly resurfaced after law-enforcement takedowns with retooled evasion techniques.

A researcher recently reverse-engineered a post-takedown Emotet sample end-to-end: the initial script dropper, the fileless in-memory payload, its anti-analysis tricks, and its encrypted command-and-control channel. This lab walks through the key stages of that analysis. Read each briefing panel carefully — the quiz below tests whether you understand why each technique works, not just that it exists.

Attack chain overview

Phishing doc / VBS script→ 2nd-stage VBS in %temp% (.txt)→ rundll32.exe loads Emotet DLL→ X.dll decrypted into RWX memory→ Relocate to %AppData% (.xnj)→ ECDH/AES key exchange→ HTTP C2 via Cookie header

1 A two-stage VBS dropper writes its second-stage script into %temp% disguised as a .txt file, then executes it directly as VBScript regardless of extension.

2 The real payload, nicknamed X.dll, is stored encrypted inside a bitmap resource of the outer DLL and is decrypted straight into an executable (RWX) memory region — it never touches disk. 
rwx = VirtualAlloc(NULL, size,
  MEM_COMMIT, PAGE_EXECUTE_READWRITE);
Decrypt(resourceBlob, rwx, size);
 Evasion
3 The main routine uses control flow flattening, which defeated the public deobfuscation tools the researcher tried and forced manual, breakpoint-driven analysis. 
while (state != EXIT) {
  switch (state) {
    case S1: ...; state = S4; break;
    case S4: ...; state = S2; break;
    // dispatcher order != real order
  }
}
 Evasion
4 Every Windows API is resolved at runtime by comparing hashes rather than through a normal import table, so static analysis shows almost nothing about functionality. 
hLib = LoadLibraryW(DecryptStr(encName));
fn = resolve_func(hLib, targetHash);
fn(args);
 Evasion
5 If not already running from %AppData%, the malware copies itself there under a randomized name with a .xnj extension, strips the Zone.Identifier (Mark-of-the-Web), and relaunches itself. 
SHGetFolderPathW(CSIDL_APPDATA, ...);
SHFileOperationW(FO_COPY, self, dst);
DeleteFileW(dst + ":Zone.Identifier");
CreateProcessW(rundll32, dst, ...);
 Persistence
6 Once relocated, it deletes every other file in its own directory — collateral damage that happens to destroy analyst tooling like IDA database files. 
for f in ListDir(homeDir):
  if f != selfName:
    DeleteFileW(f)
 Evasion
7 It generates an ECDH key pair, combines it with an embedded public key to derive a shared secret, and derives an AES key from that secret for encrypting C2 traffic. 
BCryptGenerateKeyPair(...);
BCryptSecretAgreement(priv, embeddedPub, &secret);
BCryptDeriveKey(secret, "AES", &aesKey);
 C2
8 Encrypted, base64-encoded data is transmitted inside a randomly named HTTP Cookie header to a randomly generated URI, switching to POST for larger payloads. 
Cookie: rXk3z9Qp=<base64(pubKey
  + AES_Encrypt(hostData, aesKey)
  + randomPadding)>

Detection opportunities (behavioral, not signature-based)

Because the payload is fileless and every API call is hash-resolved, the researcher notes that detection has to lean on behavior: rundll32.exe running a DLL from %AppData% with the export Control_RunDLL; a script host writing a .txt file to %temp% and immediately executing it as a script; Zone.Identifier deletion right after a copy into %AppData%; a process deleting every file in its own directory; and the specific API sequence BCryptGenerateKeyPair → BCryptSecretAgreement → BCryptDeriveKey followed by wininet traffic carrying a large base64 blob in a randomly named cookie.
